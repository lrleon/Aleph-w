# Notas de la versión 7.0.0 de Aleph-w

Idioma: [English](7.0.0.md) | Español

Aleph-w 7.0.0 es una versión mayor. Rehace la familia de arreglos (`Array`,
`MemArray`, `DynArray`, `ArrayStack`, `ArrayQueue`), hace que recorrer un
contenedor constante respete su constancia y corrige varios defectos de
seguridad de memoria de 6.x. **No es compatible a nivel de código fuente**
con 6.x: la mayoría de las rupturas son errores de compilación con un
arreglo mecánico, y unas pocas cambian el comportamiento sin aviso, así que
lea [Cambios de comportamiento](#cambios-de-comportamiento) antes de
actualizar.

Como en toda versión, recompile todo con los headers nuevos: no se promete
compatibilidad binaria (ABI) entre versiones
([`VERSIONING.md`](../../VERSIONING.md#abi-compatibility), en inglés).

## Lista para actualizar

1. Cambie `find_package(Aleph 6 ...)` por `find_package(Aleph 7 ...)`. El
   paquete usa compatibilidad `SameMajorVersion`, así que una petición de
   6.x no acepta la 7.0.0.
2. Compile y corrija los errores. Casi todos provienen de tres patrones:
   - `C::Iterator it(c)` con `c` constante: escriba
     `auto it = c.get_it();` (también compila con 6.x).
   - `Array<T> a(n)`: escriba `Array<T>::create_reserved(n)`, o consulte la
     [tabla de migración](../array-storage-contracts.md#array-construction)
     (en inglés).
   - `DynArray<T> a = n;` o un entero pasado donde se espera un
     `DynArray`: escriba `DynArray<T> a(n)`.
3. Revise el código que el compilador no puede señalar (detalles en
   [Cambios de comportamiento](#cambios-de-comportamiento)). Estas búsquedas
   encuentran los candidatos habituales:

   ```bash
   # find_index()/index_of() comparados con -1 (ahora devuelven size())
   grep -rnE "(find_index|index_of)\(" src/ | grep -E "\-1|npos"
   # alias de ArrayQueue cuyo resultado cambia cuando el buffer da la vuelta
   # (búsqueda amplia: quédese con las coincidencias sobre objetos ArrayQueue)
   grep -rnE "\.(first|get_first|top|last|get_last|pop|remove_last)\(\)" src/
   # código que esperaba que DynArray lanzara invalid_argument en entradas no escritas
   grep -rn "invalid_argument" src/
   ```

4. Los iteradores de árboles ya no asignan memoria, pero son objetos más
   grandes (hasta alrededor de 1 KiB); vea [sus tamaños](#los-iteradores-de-árboles-viven-en-la-pila).

## Cambios incompatibles

### Los contenedores constantes se recorren con `Const_Iterator`

`C::Iterator` ya no se puede construir a partir de un `const C &`. Sobre un
contenedor constante, `get_it()` devuelve el nuevo `C::Const_Iterator`,
cuyo `get_curr()` devuelve `const T &`.

```cpp
void print(const DynList<int> & l)
{
  for (DynList<int>::Iterator it(l); it.has_curr(); it.next())   // 6.x: compila; 7.0: error
    std::cout << it.get_curr();

  for (auto it = l.get_it(); it.has_curr(); it.next())           // 6.x y 7.0
    std::cout << it.get_curr();

  for (DynList<int>::Const_Iterator it(l); it.has_curr(); it.next())  // solo 7.0
    std::cout << it.get_curr();

  for (const auto & x : l)                                       // sin cambios
    std::cout << x;
}
```

`typename C::Iterator it = c.get_it();` sobre un contenedor constante falla
por la misma razón; use `auto`.

Afectados: `DynList`, `DynDlist`, `Array`, `DynArray`, `MemArray`,
`ArrayStack`, `FixedStack`, `ArrayQueue`, `FixedQueue`, `DynListStack`,
`DynListQueue`, `DynSetTree`, `DynMapTree`, las tablas hash (`DynSetHash`,
`DynMapHash` y las construidas sobre `hashDry.H`), `Random_Set` y
`Aleph::Vector`, además de los contenedores que derivan de ellos. El propio
Aleph tuvo que reescribir unos 150 de estos bucles, así que es de esperar
que sea el error más frecuente.

### Construcción de `Array`

- `Array<T>(n)` está eliminado. En 6.x significaba "vacío, con capacidad
  para `n`", pero según `T` y el tipo del argumento podía ganar un
  constructor variádico y construir el arreglo de un elemento `{n}`. Diga
  lo que quiere:

  | 6.x | 7.0 |
  |---|---|
  | `Array<T> a(n);` y luego `append()` | `auto a = Array<T>::create_reserved(n);` |
  | `Array<T> a(n); a.putn(n);` | `auto a = Array<T>::create(n);` |
  | `Array<T> a(n);` y luego `a(i) = ...` | `auto a = Array<T>::create(n);` o `Array<T> a(n, value);` |

  Cuidado: el nuevo `Array<T> a(n, value)` contiene `n` copias de `value`.
- Se eliminaron los constructores variádicos de elementos: use llaves
  (`Array<int> a{1, 2, 3}`) o el nuevo `Array<int>::build(1, 2, 3)` (vea
  [Novedades](#novedades)).
- El constructor de rango exige un iterador de entrada y un centinela
  compatible. El constructor de par de iteradores que `Special_Ctors` genera
  para los demás contenedores tiene la misma restricción, así que un par de
  enteros nunca lo selecciona.

### `DynArray`

- `DynArray(size_t)` es `explicit`: `DynArray<int> a = 10;` y pasar `10`
  donde se espera un `DynArray<int>` ya no compilan.
- `operator[]` de un `DynArray` constante devuelve `const T &` en lugar de
  un proxy, así que escribir a través de un arreglo constante ya no
  compila. Además lanza `std::out_of_range` cuando `i >= size()` (vea
  [Cambios de comportamiento](#cambios-de-comportamiento)).
- `top()`, `get_first()` y `get_last()` de un `DynArray` constante
  devuelven `const T &` (en 6.x devolvían `T &`).

### Las operaciones sobre contenedores constantes reciben `const T &`

`traverse()` sobre un contenedor constante le pasaba `T &` a la operación en
la mayoría de los contenedores. Ahora le pasa `const T &`, así que una
operación que recibe `T &` (y podía modificar el contenedor) ya no compila
ahí.

### `ArrayQueue` ya no expone su buffer

`ArrayQueue` hereda de `MemArray` con acceso protegido: ya no se convierte a
`MemArray`, y `access()`, `get_ptr()`, `get_dim()` y `get_ne()` dejaron de
ser operaciones públicas de la cola. Use `front(i)`, `rear(i)`, el
indexado o la iteración.

### Especificaciones `noexcept`

Se quitó `noexcept` donde una función puede lanzar, para que la excepción
se propague en lugar de llamar a `std::terminate`: `Array::get_first()`,
`Array::get_last()`, `ArrayStack::base()`, las funciones de geometría de
`DynArray`, el constructor, `next_ne()` y `reset_first()` de
`BinNodeInfixIterator`, y `next_ne()` de `BinNodePrefixIterator`.
`DynIntervalTree::Iterator` y `contains()`/`has()` de `DynListStack` ahora
tienen especificaciones condicionales. Solo afecta al código que verifica
estas especificaciones (por ejemplo, con `static_assert`).

## Cambios de comportamiento

Esto compila sin cambios, pero se comporta distinto.

| Cambio | 6.x | 7.0 |
|---|---|---|
| `find_index()` / `index_of()` de los mixins de `ah-dry-mixin.H` (`Aleph::Vector`, `BitArray`, `Tree_Node`, sus propias clases) cuando nada coincide | `size_t(-1)` | `size()`, como ya hacían los contenedores clásicos |
| `ArrayQueue::first()`, `get_first()`, `top()`, `pop()`, `last()`, `get_last()`, `remove_last()`, `operator[]`, `operator()` después de que el buffer circular da la vuelta | posiciones físicas: elementos equivocados | orden FIFO: el más antiguo es `first()` y el más reciente `last()` |
| `c[i]` sobre un `DynArray` constante con `i >= size()` | devolvía la casilla, o lanzaba `std::invalid_argument` si su bloque no existía | lanza `std::out_of_range` |
| Leer una entrada de `DynArray` cuyo bloque nunca se asignó (`a[i]`, `get_first()`, `c[i]` constante) | lanzaba `std::invalid_argument` | devuelve el valor por omisión; en un arreglo modificable, además asigna el bloque |
| Iterar o recorrer un `DynArray` modificable con bloques nunca escritos | se caía (bloque nulo) | funciona, y asigna los bloques que visita; use `std::as_const(a)` para leer sin asignar |
| `Array::operator()` y `MemArray::operator()` con `size() <= i < capacity()` | leían la casilla | aserción en Debug (`i < size()`); use `operator[]` para un acceso verificado |
| `Array::get_first()`, `Array::get_last()`, `ArrayStack::base()` sobre un contenedor vacío | `std::terminate` | lanzan `std::underflow_error` |
| Mover un `mpz_class`, `mpq_class` o `mpfr_class` de `gmpfrxx.h` | copiaba: el origen conservaba su valor | la construcción por movimiento deja el origen en cero (`0`, `0/1`); la asignación por movimiento intercambia los valores |
| Un rvalue pasado a `nappend()`, `ninsert()`, `append_in_container()`, `insert_in_container()`, `build_container()`, `build_array()` o `build_dynlist()` | se copiaba | se mueve: un argumento pasado con `std::move()` queda movido |
| Valor devuelto por `nappend()`, `ninsert()`, `append_in_container()` e `insert_in_container()` | la cantidad de argumentos | la cantidad de elementos que el contenedor agregó: un conjunto deja fuera las claves que ya tiene |
| Valor devuelto por `Rand_Tree::insert()` y `Rand_Tree::insert_dup()` | la raíz del árbol | el nodo insertado, como está documentado y como hacen los demás árboles |
| `verify()` de los árboles binarios de búsqueda, `is_red_black_tree()`, `is_red_black_bst()` y sus variantes `_rk` | aceptaban algunos árboles inválidos (ver [Correcciones](#correcciones)) | comprueban el invariante en cada nodo, y `verify()` también el orden de las claves |

### Los iteradores de árboles viven en la pila

Los iteradores de los árboles binarios (`BinNodeInfixIterator`,
`BinNodePrefixIterator` y el `Iterator` de las clases de árbol construidas
sobre ellos, que usan `DynSetTree` y `DynMapTree`) ya no asignan memoria
mientras recorren: la pila de nodos pendientes vive dentro del iterador,
con lugar para `Node::MaxHeight` entradas, 128 como máximo. `MaxHeight` no
cambió, pero el objeto iterador creció:

| Árbol | `Node::MaxHeight` | `sizeof` del iterador, 6.1 | 7.0 |
|---|---|---|---|
| AVL | 40 | 56 B (+ 512 B en el heap) | 368 B |
| Rojo-negro | 128 | 56 B (+ 1 KiB en el heap) | 1072 B |
| Splay, y otros árboles del `BinNode` genérico | 2048 | 56 B (+ 16 KiB en el heap) | 1072 B |

Un árbol más profundo que eso (posible en los no balanceados, como un
splay tras inserciones ordenadas) pasa los nodos pendientes al heap; en
ese caso `next_ne()` puede lanzar `std::bad_alloc`.

## Novedades

- `C::build(items...)`: un miembro estático de todo contenedor con el
  mixin funcional `FunctionalMethods` (listas, arreglos, pilas, colas,
  montículos, conjuntos y mapas) que construye el mismo contenedor que
  `C{items...}`, pero reenviando los elementos. Un rvalue se mueve, así que
  admite tipos que solo se mueven, y un elemento puede ser de cualquier tipo
  convertible implícitamente al tipo de elemento. Rigen las reglas del
  contenedor: una pila termina con el último elemento arriba, una cola con
  el primero al frente, y un conjunto o un mapa conserva el primero de dos
  elementos con la misma clave. Los contenedores derivados
  (`DynSetAvlTree`, `DynMapRbTree`, `MapOLhash`, `HashSet`, ...) se
  construyen a sí mismos, y la macro `Derived_Build(Name)` le da lo mismo a
  una clase propia. Vea
  [`FUNCTIONAL_PROGRAMMING.md`](../../FUNCTIONAL_PROGRAMMING.md#building-a-container-from-its-items-cbuild)
  (en inglés).
- `nappend()`, `ninsert()`, `append_in_container()`,
  `insert_in_container()`, `build_container()`, `build_array()` y
  `build_dynlist()` reenvían sus elementos: también admiten tipos que solo
  se mueven.
- `C::Const_Iterator` para los contenedores listados arriba
  (`ah-iterator.H`).
- `Array<T>::create_reserved(n)` y `Array<T>(n, value)`.
- `DynArray<T>(n, value)` y `DynArray::read(i)`. `read()`, `operator[]`,
  `nth()`, `find_ptr()`, `top()`, `get_first()` y `get_last()` de un
  `DynArray` constante nunca asignan memoria; una entrada nunca escrita se
  lee como el valor por omisión.
- `InlineStack<T, N>` (`tpl_arrayStack.H`): una pila de capacidad fija cuyo
  almacenamiento vive dentro del objeto; la usan los árboles balanceados
  para sus caminos de búsqueda.
- Construcción por movimiento, asignación por movimiento y `swap()` para
  `mpz_class`, `mpq_class` y `mpfr_class` en `gmpfrxx.h`. La asignación por
  movimiento y `swap()` son `noexcept`; la construcción por movimiento de
  `mpz_class` es `noexcept` con GMP 6.2 o posterior.
- `HashStats::bucket_length(i)`, la cantidad de entradas de la cubeta `i`,
  que usan las estadísticas de longitud de cadenas de las tablas hash.
- Anotaciones de contenedor de AddressSanitizer para `MemArray`
  (`ALEPH_ANNOTATE_CONTAINERS`; vea [Compilación](#compilación-cmake-y-plataformas)).

## Correcciones

- Insertar un elemento del propio contenedor (`a.append(a[0])`,
  `q.put(q.front())`, `a.insert(a[1])`) leía memoria liberada cuando el
  contenedor crecía, y una inserción al frente desplazaba el elemento antes
  de copiarlo. Vea [Inserting an element of the same container](../array-storage-contracts.md#inserting-an-element-of-the-same-container)
  (en inglés).
- `ArrayQueue`: los alias con el buffer dado vuelta (arriba); copiar y
  reservar una cola dada vuelta conserva el orden FIFO; `empty()`, `clear()`
  y `empty_and_release()` reinician ambos índices; las colas movidas se
  pueden reutilizar.
- `MemArray`, `Array` y `ArrayQueue` movidos se pueden recorrer, copiar,
  reservar y reutilizar.
- `DynArray`: iterar, recorrer o llamar a `nth()` sobre entradas nunca
  escritas ya no desreferencia un bloque nulo; crear un iterador ya no
  construye un `T` por omisión.
- Los accesos sobre contenedores vacíos lanzan en lugar de llamar a
  `std::terminate` (arriba).
- `nth()` de los mixins de `ah-dry-mixin.H` comprobaba su límite con
  `n + 1`, que desbordaba con `n == SIZE_MAX` y devolvía una referencia nula.
- `append_in_container()` e `insert_in_container()` tomaban un `size_t`
  lvalue en primera posición como su contador interno en lugar de
  insertarlo.
- `FixedQueue`: `front(i)` leía fuera del buffer cuando la cola había dado
  la vuelta, y copiar una cola dada vuelta o llena leía fuera del buffer o
  no copiaba nada.
- `DynSkipList`: el `find()` constante no compilaba, y `append()` de un
  rvalue lanzaba con una clave que ya estaba en el conjunto, en lugar de
  devolverla como hace la sobrecarga para lvalues.
- Los caminos de búsqueda de los árboles AVL y rojo-negro reservan un
  lugar para el nodo cabecera: un árbol tan alto como su `Node::MaxHeight`
  (40 en los nodos AVL) desbordaba su camino por una entrada.
- `HtdRbTreeRk`: una inserción que terminaba con una rotación doble dejaba
  los contadores de subárbol con uno de menos desde el nodo nuevo hasta la
  raíz, así que `size()`, `select()` y `position()` daban resultados
  erróneos (insertar 1, 3, 2 daba un `size()` de 2).
- `Splay_Tree::remove()` perdía nodos en un árbol con claves repetidas
  (`insert_dup()`): eliminar una clave podía descartar otros nodos que la
  tenían. `Splay_Tree_Rk` no estaba afectado.
- `Rand_Tree::insert()` e `insert_dup()` devolvían la raíz del árbol en
  lugar del nodo insertado, así que `insert_dup()` de un `DynSetTree` sobre
  `Rand_Tree` devolvía la dirección de otra clave.
- Las funciones que validan un árbol dejaban pasar defectos.
  `is_red_black_tree()` buscaba un nodo rojo con hijo rojo solo en la raíz
  y sus dos hijos, y comparaba los nodos negros solo de los caminos que
  terminan en una hoja; `verify()` de `Avl_Tree`, `Avl_Tree_Rk`,
  `TdRbTree`, `Treap`, `Treap_Rk` y `Rand_Tree` no comprobaba el orden de
  las claves, ni el de `Treap_Rk` sus contadores; `DynSetTree::verify()`
  comprobaba el orden con el comparador por omisión, y daba falso con un
  conjunto válido que usara otro; `HtdRbTree::verifyRedBlack()` no
  compilaba. Ahora cada una comprueba su invariante en cada nodo, en tiempo
  lineal, y `verifyRedBlack()` devuelve un `bool`. La nueva
  `Tests/search_trees_battery_test.cc` ejecuta los 14 tipos de árbol contra
  un `std::multiset` con `verify()` después de cada operación: todos los
  órdenes de inserción de hasta 8 claves, todos los de eliminación de
  hasta 7, secuencias aleatorias largas y los órdenes adversos.
- Documentación: `rbNode.H` y `tpl_rb_tree.H` contaban «la raíz es negra»
  entre las propiedades de los árboles rojo-negro. Ninguna de las seis
  implementaciones la impone (el único nodo de un árbol es rojo), y no les
  hace falta: una raíz roja tiene hijos negros, así que la altura sigue
  siendo a lo sumo 2 log2(n + 1). La documentación ahora lo dice, y
  `verify()` acepta una raíz roja como antes.
- Windows: `ah_cpp_compat_test` chocaba con la función global
  `::unexpected()` de la UCRT; MSVC caía en `Pair(key, Data())` al buscar en
  `DynMapHash` y exigía un `Data` con constructor por omisión;
  `point_utils_header_test` necesitaba un operador de `libgmpxx` que no
  enlaza en Windows.

## Compilación, CMake y plataformas

- **Sanitizers.** Con `ALEPH_USE_SANITIZERS=ON`, `MemArray` envenena las
  casillas reservadas más allá de `size()` (opción
  `ALEPH_ANNOTATE_CONTAINERS`, activada por omisión). La macro cambia el
  layout de `MemArray` bajo ASan, así que el target `Aleph` ahora la
  publica, junto con las opciones de los sanitizers, a sus consumidores y
  al paquete CMake instalado. Vea
  [Logical bounds and AddressSanitizer](../array-storage-contracts.md#logical-bounds-and-addresssanitizer)
  (en inglés).
- **Clang con libc++ fuera de macOS.** `gmpfrxx_test` se omite, como ya
  ocurría con `k2tree_test`: el `libgmpxx` del sistema está compilado con
  libstdc++. Vea [`docs/ci_sanitizer_policy.md`](../ci_sanitizer_policy.md)
  (en inglés).
- **Plataformas.** La CI cubre Linux (GCC y Clang, con jobs de ASan, UBSan,
  TSan y MSan), macOS (Intel y Apple silicon) y Linux arm64. En Windows
  (MSVC y clang-cl), la compilación de la CI se detenía en un error
  temprano desde la 5.2.0, lo que ocultaba fallos posteriores; esta versión
  corrige las causas encontradas hasta ahora.

## Nota sobre la política de deprecación

[`VERSIONING.md`](../../VERSIONING.md#deprecation-procedure) (en inglés)
pide un período de deprecación antes de eliminar una API pública.
`Array<T>(n)`, los constructores variádicos de `Array` y la construcción de
`C::Iterator` a partir de un contenedor constante se eliminaron en esta
versión mayor sin ese período. El error de compilación señala cada línea
afectada, y la migración es mecánica.
