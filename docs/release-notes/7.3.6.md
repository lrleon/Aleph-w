# Aleph-w 7.3.6 release notes

Language: English | [Español](7.3.6.es.md)

Aleph-w 7.3.6 is a patch release of the linear programming solvers of
`Simplex.H`, which gave wrong answers that looked right. Against an
exact oracle, 7.3.5 got right 32 970 of the 124 092 programs of a small
domain (up to two variables and two constraints, data in {-1, 0, 1},
every type of constraint, maximizing and minimizing): it reported
infeasible programs as solved, read wrong solutions, ignored negative
right-hand sides, and gave wrong shadow prices and ranges. 7.3.6 gets
them all right. `Simplex` solves in two phases, scales the program
before solving it, and no longer cycles; `RevisedSimplex` has a first
phase, and refactorizes its inverse of the basis. On the programs of
the benchmark, which 7.3.5 solved right, `Simplex` runs 3 % to 44 %
fewer instructions, and it solves the cube of Klee and Minty with one
pivot instead of 1023.

It is source compatible with 7.3.5, but for the changes listed in the
[Upgrade notes](#upgrade-notes). As with every release, recompile
everything against the new headers
([`VERSIONING.md`](../../VERSIONING.md#abi-compatibility)).

## Upgrade notes

1. `find_package(Aleph 7 ...)` accepts 7.3.6.
2. `solve()` of `Simplex` and of `RevisedSimplex` returns `Unfeasible`
   for a program without feasible points, where it could return
   `Solved`, with a point that broke the constraints, or `Unbounded`;
   and it takes a constraint with a negative right-hand side as
   written, where it ignored it. Code that took the state or the
   solution of such a program for granted gets other results.
3. `shadow_price()` is the change of the optimum per unit increase of
   the right-hand side: when maximizing, >= 0 for a `<=` constraint and
   <= 0 for a `>=` one; when minimizing, the other way. 7.3.5 gave the
   opposite sign when maximizing, and 0 for an `=` constraint.
   `rhs_sensitivity()` gives its bounds in order, where they came
   reversed, and `objective_sensitivity()` the values of the
   coefficient, where it gave reversed changes. Code that corrected the
   signs or the order must no longer do it.
4. `update_rhs_and_reoptimize()` applies the change of an `=`
   constraint, which it lost, and that of a `>=` one in its direction,
   which it reversed.
5. When a program has several optimal solutions, `solve()` may give
   another one than 7.3.5, with the same optimum: the scaling and the
   first phase change the choices of Dantzig's rule. A run of degenerate
   pivots switches to Bland's rule until a pivot improves the objective,
   so that `solve()` always ends.
6. The tolerance of `set_epsilon()` applies to the scaled program: a
   value is taken as zero when its magnitude is below it, and a
   right-hand side when it is below it times the largest magnitude of
   the right-hand sides, if this one is above 1. The default does not
   change.
7. `verify_solution()` checks too that the variables are >= 0, and
   holds each constraint up to a tolerance relative to the magnitude of
   its terms, where it took an absolute one.
8. `RevisedSimplex::set_refactorization_frequency()` throws
   `std::invalid_argument` for 0, which 7.3.5 took, so that
   `print_stats()` then divided by zero.

## Fixes

- Infeasible programs came out as solved: `solve()` used a Big-M of
  `1e9`, and its check of the artificial variables at the end was an
  empty `if`, so that `x <= 0, x >= 1` gave `Solved`, and so did
  `min 1e12 x, x >= 1`, with `x = 0`. It solves in two phases now: the
  first one minimizes the sum of the artificial variables, and the
  program is infeasible if it stays above zero; an artificial variable
  never enters the basis again.
- The solution was read from the columns that looked like unit
  vectors, so that two columns could take the same row:
  `max x + y, x + y <= 1` gave `x = y = 1`. The basic variable of each
  row is kept, and `load_solution()` reads it.
- A negative right-hand side was ignored: the ratio test skipped its
  row, so that `max -x, -x <= -1, x <= 3` gave `x = 0`, and
  `max x, x <= -1` came out unbounded. Such a row is multiplied by -1,
  which swaps `<=` and `>=`.
- Dantzig's rule cycled forever on Beale's program.
- In the example of the class documentation, the shadow prices came out
  as -20 and -10, for 20 and 10, and as 0 when its first constraint is
  an `=`; the ranges of its right-hand sides as `[60, 30]` and
  `[80, 40]`, for `[30, 60]` and `[40, 80]`; and those of its costs as
  `[20, -10]` and `[10, -10]`, for `[30, 60]` and `[20, 40]`. They read
  the column of the inverse of the basis of each row now, and take the
  rows multiplied by -1 into account.
- `update_rhs_and_reoptimize()` lost the change of an `=` constraint,
  and reversed that of a `>=` one. `dual_solve()` no longer lets an
  artificial variable enter the basis, and reports as infeasible a
  change that the artificial variable of a redundant constraint cannot
  take.
- With data of order 1e-6, a rounding error could pass for a pivot, so
  that an unbounded program came out solved, with an optimum of about
  -1.03e11. The program is scaled now: each constraint, each column and
  the objective are multiplied by a power of two, which changes no
  digit, and the results are scaled back.
- `print_matrix()`, `latex_matrix()` and `latex_solve()` did not
  compile: they called a `float_f()` that does not exist anywhere.
  `latex_linear_program()` wrote `<=` for every constraint.
- `RevisedSimplex` started from the slack variables whatever the signs
  of the right-hand sides, so that `max x, x <= -1` gave `x = -1`; it
  never refactorized its inverse of the basis, although its
  documentation said so; and it allocated an m×m matrix in each pivot.
  It has a first phase for the negative right-hand sides now, updates
  the inverse in place, and refactorizes it every
  `set_refactorization_frequency()` pivots.

## Tests

- `simplex_exhaustive_test`, new, checks the solvers against an oracle
  that enumerates the vertices in exact integer arithmetic: every
  program of the small domain above (the state, the optimum, the
  solution, the shadow prices as an optimal solution of the dual
  program, the reduced costs, and Bland's rule); 1500 random programs
  with the ranges of the sensitivity analysis, at their bounds and just
  beyond, and `update_rhs_and_reoptimize()`; 400 larger ones;
  `latex_solve()`; `RevisedSimplex`, with a refactorization every 1, 2,
  7 and 50 pivots; and programs with their data multiplied by 1e6, by
  1e-6, and with each row, each column and the objective multiplied by
  its own power of ten. Its random programs come from the raw numbers
  of `std::mt19937_64`, the same with every standard library.
- `Simplex_test`: the tests that accepted a wrong answer check the right
  one, and new tests cover each defect above, Beale's program, the cube
  of Klee and Minty, zero rows, a zero objective, redundant and
  inconsistent equalities, the sensitivity in other units, subnormal
  magnitudes, the LaTeX output, and every public member that no test
  called.
- `tpl_multicommodity_test`: `MediumNetwork` passed only because
  infeasible programs came out as solved. Its grid had arcs only to the
  right and down, so that the commodity from the top right corner to
  the bottom left one had no path. Its arcs go both ways now, and its
  cost is checked; a new test checks that the grid of before is
  reported infeasible.

## Performance

Counted with cachegrind, with GCC 14 and Clang 22 at `-O2`, against
7.3.5, on programs that 7.3.5 solves right; both give the same optimum:

- A maximization with 30 dense `<=` constraints and 30 variables runs
  28.5 % (GCC) and 28.2 % (Clang) fewer instructions, with 14 pivots
  instead of 20.
- A diet minimization with 15 `>=` constraints and 20 variables, 43.8 %
  and 44.0 % fewer, with 24 pivots instead of 41.
- A transportation minimization with 5 supplies (`<=`) and 6 demands
  (`=`), 4.4 % and 3.5 % fewer, with 10 pivots.
- The cube of Klee and Minty of 10 dimensions, 99.6 % and 99.7 % fewer:
  one pivot instead of 1023.
- `tpl_multicommodity` on a 4×4 grid with arcs both ways and 2
  commodities, 10.0 % and 7.6 % fewer.

The scaling changes the choices of Dantzig's rule, which depend on the
units of the columns: on these programs it takes fewer pivots.

  `reduced_cost()`, `rhs_sensitivity()`, `objective_sensitivity()`,
  `set_epsilon()` and `verify_solution()` say what they give.
