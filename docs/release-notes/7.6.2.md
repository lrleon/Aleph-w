# Aleph-w 7.6.2 release notes

Language: English | [Español](7.6.2.es.md)

Aleph-w 7.6.2 is a patch release of the macros of `ah-errors.H`. A macro
that throws wrote its message in a `std::ostringstream` that lived in
the frame of the function that checks, and GCC does not inline a
function whose frame grows so much: a checked access, as
`Array::operator[]`, was a call, and so was any small function that
checks with a macro. The stream is out of that frame now. With GCC, a
loop that reads through `operator[]` runs a fifth of its instructions,
HLPP with an integer flow half of them, and the cycle canceling a
quarter less; with Clang 18, the flows run up to 11 % fewer, and
Bellman-Ford up to a third. The messages do not change.

It is source compatible with 7.6.1. As with every release, recompile
everything against the new headers
([`VERSIONING.md`](../../VERSIONING.md#abi-compatibility)).

## Upgrade notes

1. `find_package(Aleph 7 ...)` accepts 7.6.2.
2. The exceptions of the macros of `ah-errors.H` have the type, the
   place and the text of 7.6.1, and their items are evaluated and read
   as before. A macro that throws takes its stream from the heap, where
   the frame of its caller gave it: it makes one allocation more than in
   7.6.1, which a test that counts the allocations of a path that throws
   sees. If that allocation fails, the macro throws `std::bad_alloc` and
   does not evaluate its items; in 7.6.1, a stream whose growth failed
   gave a shorter message.
3. The place of an error, `(file:line) | `, is written inside the
   library, by the inserters of the standard library. An overload of
   `<<` for an rvalue `std::ostringstream` that is visible where a macro
   is used takes the items of that use, and no longer the place: code
   that needed it to change the type of the place does not compile.
4. `ah-errors.H` defines `AH_ERROR_COLD` and
   `Aleph::error_detail::Message_Stream`, for its macros alone: they are
   not an interface.

## Known limits

- **A check still costs its comparison.** A loop of six items that makes
  two checked accesses per item takes 1.25 to 1.36 times the time of its
  unchecked form with GCC 13 and 14, and 1.04 with Clang 18. Where the
  range is guaranteed, `operator()` of an `Array` and the `_ne`
  accessors of the iterators read without the check.
- **With GCC 14, a few algorithms run more instructions than with
  7.6.1:** Kruskal 0.6 %, `test_for_cycle()` on an `Array_Graph` 2.4 %,
  and four other depth-first searches 0.4 to 1.0 %. In cycles they take
  the same, within what the alignment of their code moves them, but for
  `paint_subgraphs()` on an `Array_Graph`, which takes 0.7 to 0.8 %
  more. With Clang 18 none runs over 0.1 % more.
- **A loop that appends can take more than with 7.6.1 where it is
  written in `main()`.** With Clang 18, one that appends 32 items to an
  `Array` takes 30 % more cycles with 0.7 % fewer instructions, and its
  time goes with the position of the stack; in a function it takes
  1.6 % more. With GCC 13 and 14, a queue and a stack in `main()` take
  1.6 to 2.7 % more. And with Clang 18 the constructor of `MemArray` is
  no longer inlined, 28 instructions more for each array.
- **The limit of 7.6.1 with GCC 13 is gone.** In the benchmark that its
  notes name, `most_negative_cycle_bounded()` takes 40 % less time than
  with 7.6.1, and a third less than with 7.6.0; with GCC 14, a third
  less; with Clang 18, 3 % more.

## Tests

- `Tests/ah_errors_message_test.cc`, fourteen tests of the messages of
  the macros: the place, with its line, and the items of their 46 forms;
  the items that a stream takes (literals, characters, numbers,
  pointers, strings, a type with its own `<<`, an enumeration,
  bit-fields) and its manipulators, against the same items written in a
  stream; the temporaries of the items, which live until the macro
  throws; each item evaluated once, in order and only to throw, and read
  when it is inserted; the macro as an argument of another; the stream,
  which is one pointer and has the type of the temporary stream of the
  former macros, and which dies once when its exception leaves, be it
  that of the macro or that of an item; an overload of the caller, which
  takes its items and not the place; eight threads, each of which writes
  its own messages; a message that an item of another throws and
  catches; and the checked accesses out of range of `Array`, `MemArray`,
  `SmallVector`, `DynArray`, `ArrayQueue` and `BitArray`, which throw
  with their text.
- `Tests/ah_errors_stream_failure_test.cc`, three tests with a global
  `operator new` that fails on demand: without memory for its stream, a
  macro throws `std::bad_alloc` and evaluates no item; whatever
  allocation fails, it throws `std::bad_alloc` or its exception, with
  the start of its message; and a place that throws frees the stream.
- `Tests/memarray.cc`, a test of the growth of a full array from each of
  its slots and at each position, with a scalar and with a string.
- The 6.36 million exceptions that the tests of 7.6.1 throw carry the
  same messages: an interposer of `__cxa_throw` recorded the type and
  the text of each one with both versions. Only the line of the 18
  messages of `tpl_memArray.H` moves, by the lines added above them.

## Performance

Instructions against 7.6.1 (cachegrind, GCC 14 and Clang 18 at
`-O2 -DNDEBUG`, each case built alone), with the same results in every
case:

| Case | GCC 14 | Clang 18 |
|---|---|---|
| A loop through `operator[]`, per cycle | 609 → 125 | 343 → 114 |
| HLPP, integer flow | −50 % | −6 % |
| HLPP, floating flow | −1.4 % | −8 % |
| Cycle canceling | −22 to −25 % | −3 to −4 % |
| Network simplex | −1.7 to −6.8 % | −5 to −6.5 % |
| Edmonds-Karp, Ford-Fulkerson | −2 to −3 % | −1.5 to −1.8 % |
| Dinic | −0.7 to −1 % | −10 to −11 % |
| Capacity scaling | 0 to −1.5 % | −1.6 % |
| Successive shortest paths | within 0.1 % | −0.6 to −0.7 % |
| Bellman-Ford | within 0.3 % | −15 to −33 % |
| Its faster variant on an `Array_Graph` | −32 % | −6 % |
| The planarity test | −1.1 % | −6.5 % |
| Kruskal | +0.6 % | −2.8 % |
| `compute_stats()`, Mo, the R-trees | within 0.1 % | the same |
| The depth-first searches | −2.3 to +1.0 % | −7.0 to +0.1 % |
| `test_for_cycle()` on an `Array_Graph` | +2.4 % | the same |

The loop of the first row reads three arrays; through `operator()` it
takes 76 instructions per cycle, and with GCC 13 it goes from 650 to 125
of them. The depth-first searches are 29 algorithms, each on a
`List_Graph` and on an `Array_Graph`; `test_for_cycle()` on an
`Array_Graph` is the one out of their range.

A loop that sums k items of an `Array`, in time through `operator[]`
against `operator()` (one core, the least of 5 runs, 7.6.1 → 7.6.2):

| | GCC 14 | GCC 13 | Clang 18 |
|---|---|---|---|
| k = 6 | 3.92 → 1.00 | 3.44 → 1.00 | 1.80 → 1.00 |
| k = 1024 | 5.55 → 1.06 | 5.55 → 1.06 | 5.47 → 1.06 |
| k = 6, two accesses per item | 6.18 → 1.36 | 6.39 → 1.25 | 3.86 → 1.04 |
| k = 1024, two accesses per item | 5.33 → 1.04 | 5.89 → 1.05 | 5.30 → 1.04 |

What runs more instructions with GCC 14 does not take more cycles
(perf, one core, the mean of four alignments of the code): −1.8 to
+0.4 %, but for `paint_subgraphs()` on an `Array_Graph`, +0.7 to +0.8 %;
and `test_for_path()` on a `List_Graph`, which the alignment alone
moves between −6.5 and +8.8 %, takes −0.3 to +0.6 %: its hot loops are
the same, instruction by instruction.

`benchmarks/ca/bench_wolfram_30_1d.cc`, a one-dimensional automaton of
10^6 cells for 1 000 steps, takes half the time with GCC 13 (3.82 →
1.90 s, the least of three runs) and with GCC 14 (3.91 → 1.98), and
12 % less with Clang 18 (7.70 → 6.75). In the performance gate of the
CI, with GCC 13.3 on an AMD EPYC 7763, it takes 4.4 s where it took
12.0 in the three pull requests before; `gray_scott_512` takes 7 % less
there, and the other four benchmarks are within their noise.

The growth of a full `MemArray` is out of line. With the block that
throws smaller, GCC 14 copied it into `put_item()`, the body of
`append()`, which was then too large for the loops that append to inline
it. It moves the items with a loop for each side of the new one, and
takes a scalar item as a copy, made only when the array grows: by
reference, the item of a loop that appends lived in memory, and the loop
stored it at each step. A loop that appends 1024 items, in cycles an
item (perf, one core, the mean of sixteen positions of the stack,
7.6.1 → 7.6.2):

| | GCC 14 | GCC 13 | Clang 18 |
|---|---|---|---|
| To an `Array` | 3.94 → 2.10 | 4.53 → 3.67 | 4.75 → 4.01 |
| To an `Array` by reference | 5.44 → 3.31 | 5.41 → 3.72 | 5.55 → 4.05 |
| To a `MemArray` already reserved | 2.05 → 0.80 | 2.08 → 2.04 | 2.15 → 2.11 |
| To an `Array` of pointers | 4.01 → 2.28 | 4.59 → 3.77 | 4.95 → 4.29 |
| To an `Array` of pairs | 5.87 → 5.06 | 7.32 → 6.48 | 6.82 → 6.30 |
| A filter into an `Array` | 4.31 → 3.82 | 4.39 → 3.87 | 5.02 → 4.36 |
| To an `Array`, in `main()` | 2.10 → 2.05 | 5.30 → 3.66 | 4.77 → 3.98 |
| To an `ArrayStack`, in `main()` | 2.20 → 2.24 | 4.41 → 3.42 | 4.92 → 4.17 |

The loops of the first six rows are in a function; GCC 14 inlined the
whole growth where the loop is in `main()`.

The code of the tests is 1.8 % smaller, that of the examples 7.2 % and
the static library 7.3 %.
