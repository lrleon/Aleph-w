# Aleph-w 7.1.0 release notes

Language: English | [Español](7.1.0.es.md)

Aleph-w 7.1.0 is a minor release. A new overload of
`CancellationToken::notify_on_cancel()` delivers a cancellation to the
threads that wait on a condition variable without polling, and the old one
is deprecated. It also fixes the open addressing hash tables, which could
run out of empty buckets while far from full, and their iterator, which read
past the end of the buckets when it deleted the last key.

It is source compatible with 7.0.1, except for taking the address of
`notify_on_cancel` without naming its type ([Upgrade notes](#upgrade-notes)).
As with every release, recompile everything against the new headers
([`VERSIONING.md`](../../VERSIONING.md#abi-compatibility)).

## Upgrade notes

1. `find_package(Aleph 7 ...)` accepts 7.1.0.
2. `CancellationToken::notify_on_cancel(cv)` is deprecated, and calling it
   gives a compiler warning. Replace it with `notify_on_cancel(cv, mutex)`,
   where `mutex` is the mutex that the waiters on `cv` hold, and declare the
   guard before the lock:

   ```cpp
   CancellationToken::ConditionVariableRegistration registration;
   std::unique_lock<std::mutex> lock(mutex);
   registration = token.notify_on_cancel(cv, mutex);
   cv.wait(lock, [&] { return ready or token.stop_requested(); });
   ```

   A wait with a timeout, which the old overload needed to see a
   cancellation that it missed, is no longer needed.
3. `auto f = &CancellationToken::notify_on_cancel;` no longer compiles,
   since there are two overloads. Give the type of the one wanted:

   ```cpp
   using Token = Aleph::CancellationToken;
   Token::ConditionVariableRegistration
     (Token::*f)(std::condition_variable &, std::mutex &) const =
       &Token::notify_on_cancel;
   ```

4. In an open addressing table that resizes itself, an insertion can now
   rebuild the table in place as well; as after a growth, the pointers to its
   keys are not valid after it. A table built with `with_resize = false`
   never rebuilds itself, as before.

## New

- **`CancellationToken::notify_on_cancel(cv, mutex)`.** A cancellation takes
  and releases `mutex` before it notifies `cv`, so it cannot come between the
  check of the token and the wait: a waiter that checks `stop_requested()`
  under `mutex` after registering, and waits on `cv` for that check, always
  wakes up. Each call makes its own registration; destroying or assigning the
  guard ends it, and moving the guard transfers it.
- **`BoundedChannel`** uses it: an operation that waits with a token sees the
  cancellation without waking up every 10 ms, as it did in 7.0.1.

## Deprecated

- `CancellationToken::notify_on_cancel(std::condition_variable &)`. Use
  `notify_on_cancel(cv, mutex)` instead. It keeps working as before, and it
  may be removed in 8.0.0, as the
  [deprecation procedure](../../VERSIONING.md#deprecation-procedure)
  provides.

## Behavior changes

### Concurrency

- **`request_cancel()` can wait.** For each registration made with a mutex,
  it takes and releases that mutex, one at a time, so it waits while a waiter
  holds it outside its wait. To avoid a deadlock, treat requesting the
  cancellation, and ending such a registration, as taking its mutex: not
  while holding it, nor while holding another mutex that a thread may take
  while it holds that one. Declaring the guard before the lock, as above,
  ends the registration after the lock has released the mutex.
- **`BoundedChannel`.** Its element operations run under the mutex of the
  channel, so they must not request the cancellation of a token that an
  operation of the same channel waits with.

### Hash tables

- **Removed keys.** In an open addressing table that resizes itself, the
  buckets of removed keys count as used. When they take the table to its
  upper threshold, it is rebuilt without them: in place if the keys alone
  fill less than half of the threshold, and twice as large otherwise. So the
  table can double while its keys are under the threshold.
- **Tables that do not resize.** A table built with `with_resize = false` is
  never rebuilt by itself, so that its keys do not move. After many removals,
  `rehash()` clears the buckets of the removed keys.
- **Iterator.** `del()` leaves the iterator at the end when it deletes the
  last key.

## Fixes

- **Cancellation.** A cancellation could come between the check of the
  token and the wait of a thread, and be lost; 7.0.1 worked around it in
  `BoundedChannel` by checking the token again every 10 ms.
- **Hash tables.** The buckets of removed keys did not count to grow an open
  addressing table or to decide that it was full. Insertions and removals
  could then leave it without empty buckets far from its threshold, and a
  search that missed, as well as every insertion, went through the whole
  table: with random keys, a linear probing table of 1103 buckets got to 534
  keys and no empty bucket. The `del()` of the iterator read past the end of
  the buckets when it deleted the last key in bucket order and other keys
  were left before it.

## Documentation

- `CancellationSource` says that several threads may cancel the same source
  at once, and that `reset()` and assignment must not run at the same time as
  another use of it.
- [`VERSIONING.md`](../../VERSIONING.md) lists 7.1.0.
