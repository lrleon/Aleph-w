# Aleph-w 7.1.2 release notes

Language: English | [Español](7.1.2.es.md)

Aleph-w 7.1.2 is a patch release that fixes three functions of `primes.H`:
`Primes::next_prime_number_greater_than()` skipped `n + 1` for an even `n`,
`Primes::next_prime()` did not return `n` for a prime `n` above its table,
and `Primes::is_prime()` overflowed its counter for large 64-bit numbers.
The hash tables size themselves with `next_prime()`, whose results do not
change up to 3972250003, the last prime of its table.

It is source compatible with 7.1.1. As with every release, recompile
everything against the new headers
([`VERSIONING.md`](../../VERSIONING.md#abi-compatibility)).

## Upgrade notes

1. `find_package(Aleph 7 ...)` accepts 7.1.2.
2. Code that calls `next_prime_number_greater_than()` gets the smallest
   prime greater than `n`, as its documentation says: 5 for 4, 11 for 10
   and 101 for 100, where 7.1.1 gave 7, 13 and 103.
3. Above 3972250003, `next_prime(n)` now gives `n` for a prime `n`, so a
   hash table created with a size above it, or that grows past it, may get
   a different size than with 7.1.1.

## Fixes

- **`next_prime_number_greater_than(n)` skipped `n + 1` for an even `n`.**
  It was wrong for 9590 of the `n` below 100000. It now returns the
  smallest prime greater than `n`, and throws `std::domain_error` for every
  `n` from `ULONG_MAX - 2` on, as no prime greater than `ULONG_MAX - 2`
  fits in an `unsigned long`. For `ULONG_MAX - 2` it returned 3.
- **`next_prime(n)` above its table** returned the smallest prime greater
  than `n`, with the skip above: for a prime `n` it returned the next
  prime (`next_prime(3972250019)` was 3972250021), and for an even `n` it
  could miss `n + 1` (`next_prime(3972250018)` was 3972250021 too). It now
  returns the smallest prime that is `>= n`, as below 101, and throws
  `std::domain_error` when none fits in an `unsigned long`.
  `next_prime(ULONG_MAX - 2)` returned 3.
- **`is_prime(n)` counted with an `int`** up to `sqrt(n)`. Where
  `unsigned long` has 64 bits, as on Linux and macOS, the counter
  overflowed for an `n` of at least `(2^31 - 1)^2`, about 4.6 · 10^18,
  with no factor up to `2^31 - 1`. That is undefined behavior: with GCC 14
  at `-O2`, `is_prime(18446744073709551557)`, the largest 64-bit prime,
  returned `false` when the argument was a constant, and did not return
  within a minute when it was not. It now counts with an
  `unsigned long`, and for every other `n` its results do not change. It
  still uses trial division, so for a prime near `ULONG_MAX` it takes
  about 2^32 divisions.

## Documentation

- `next_prime()` says what it returns: within its table, the first prime
  of the table that is `>= n`, which is often larger than the smallest
  one (`next_prime(2206)` is 2309, although 2207 is prime); below 101 and
  above the table, the smallest prime that is `>= n`.
- `check_primes_database()` says that it checks that the table is
  strictly increasing, as the binary search of `next_prime()` needs. It
  said that it checks that the entries are prime.
- [`VERSIONING.md`](../../VERSIONING.md) lists 7.1.2.
